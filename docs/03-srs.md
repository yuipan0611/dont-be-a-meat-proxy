## 0. 名詞與元件對應

| PRD 用語 | 系統裡對應的東西（G1 架構） |
|---|---|
| Hub | VPS 上的服務組合：Agent Mail Rust（一組一容器）＋ Caddy＋〔上線〕Hindsight＋bank 代理＋Discord bot |
| 組 | 一個 Agent Mail 容器＋一個 Hindsight bank＋一個 GitHub repo。S1 只有一組（維護者 自己） |
| agent | 在 Agent Mail 註冊的一個身分，綁一台裝置上的一個 AI 工具 |
| 項目 | 一則 Agent Mail 訊息，帶「項目類型」（SR-MSG-01） |
| 連線 token | 每台裝置一把、由 Caddy 驗證的個人 bearer token（SR-ID） |
| 正式紀錄 | 交接、求助、決策、確認結果存在 Agent Mail；任務存在 GitHub Issues；Hindsight 只是索引（SR-KEEP） |

時間：伺服器時間為準，以 UTC ISO 8601 儲存，顯示時用 Asia/Taipei。所有「滿 N 分鐘」的判斷都用伺服器收到的時間，不用 client 自報的時間。

## 2. 系統規則

### 2.1 身分與連線 token（SR-ID）

| ID | 批次 | 規則 | 回指 |
|---|---|---|---|
| SR-ID-01 | MVP | 每台裝置的每個 AI 工具用自己的一把個人 bearer token。Caddy 對**每一個** HTTP 請求驗證（含 MCP、網頁 UI、API、health）；沒有 token、token 錯誤或已撤銷 → 401（E-AUTH）。 | US-12、13 |
| SR-ID-02 | MVP | Agent Mail 後端只聽 127.0.0.1，外部不能直連（F-01b：後端的 liveness 路由是公開的）。外部只開 Caddy 的 HTTPS 入口。 | US-12 |
| SR-ID-03 | MVP | 撤銷＝把該 token 從 Caddy 允許清單刪掉並 reload。reload 成功後，該 token 的**下一個請求**被拒（含已開著的 session）；其他 token 照常（F-01b E5）。已進入後端的請求不保證中斷。 | AC-12.4 |
| SR-ID-04 | MVP | MVP 期間 token 由 維護者 手動產生、手動填進設定、手動撤銷；不經 Discord。 | US-12 |
| SR-ID-05 | 上線 | `/connect`：只有成員能用；回覆是 ephemeral；每次發一把**新的**裝置 token，舊 token 不因此失效；撤銷某一把不影響其他把。token 只出現在這則 ephemeral 回覆，之後不能再查看原值。 | AC-12.1、12.3～12.5 |
| SR-ID-06 | 上線 | 成員＝Discord user ID 在成員名單上。S1 名單只有 維護者。名單來源（S2）待確認。 | AC-08.6、12.3 |
| SR-ID-07 | MVP | 寄件者身分由 Hub 依該 session 註冊的 agent 決定，不採用內容裡自報的作者。S1 一組內共用同一個後端憑證（F-01b），組內互信；S2 起的冒名防護 **待對齊 T7**。 | AC-01.1、04.4 |
| SR-ID-08 | 上線 | 寫入 Hindsight 時，代理依 token 強制填作者，不採用 agent 自填的 `metadata.author`（F-05 §4）。 | R-1、AC-04.4 |

### 2.2 項目與訊息（SR-MSG）

規則如何配合主流程：寄件 agent 送出 → Hub 驗證欄位 → 保存 → 回傳 ID → 〔上線〕通知。任何一步失敗都不保存、不通知。

**資料字典**

| 欄位 | 誰決定 | 合法值／規則 | 缺漏或無效時 |
|---|---|---|---|
| 項目 ID | 伺服器 | 保存成功才有；不重複使用 | — |
| 項目類型 | 寄件者 | `任務`／`交接`／`求助`／`決策`，四選一（決策 #6） | E-FIELD，不保存 |
| 請求性質 | 寄件者先標，收件端最後判定 | `question`／`action`（SR-MSG-06） | 寄件者沒標 → 收件端當 `action` |
| 作者 agent、成員 | 伺服器 | 依 SR-ID-07 | — |
| 收件者 | 寄件者 | 同組已註冊的 agent，至少 1 個 | E-RCPT（FR-02） |
| 內容 | 寄件者 | 純文字／Markdown，逐字保存；長度上限 **待確認**（AC-01.1 至少要 1,500 字） | 空白 → E-FIELD |
| 連結 | 寄件者 | 只放 PR、commit、Issue 的 URL | — |
| 附件 | — | **不允許**（NG-03；F-01b E6 證實附件路徑可讀到別組檔案） | E-ATTACH，不保存 |
| idempotency key | 寄件端 | 每則新項目一個新值 | 沒帶 → 照常保存，但不保證防重複 |
| 送出時間 | 伺服器 | UTC | — |
| 狀態 | 伺服器 | 見下方狀態表 | — |

| ID | 批次 | 規則 | 回指 |
|---|---|---|---|
| SR-MSG-01 | MVP | 項目類型與請求性質必須存進 Agent Mail 的訊息裡，收件端與 Discord 都能讀到。存放方式（主旨前綴或既有欄位）**待對齊 T7**，Agent Mail 本身不改。 | US-01 |
| SR-MSG-02 | MVP | 內容逐字保存、逐字送達：收到的內容和送出的一字不差（含換行、連結、繁體字）。 | AC-01.1 |
| SR-MSG-03 | MVP | 帶附件的送出一律拒絕（E-ATTACH）。部署上 Agent Mail 容器只掛自己組的 volume（F-01b E6）。 | AC-01.4 |
| SR-MSG-04 | 上線 | 疑似密碼的送出拒絕（E-SECRET），內容不保存。最少要擋：`sk-` 開頭的長字串、`ghp_`／`github_pat_` 開頭、`-----BEGIN ... PRIVATE KEY-----`。完整清單、誤判處理、在哪一層擋（client 或代理）都 **待確認／待對齊 T7**。 | AC-01.3 |
| SR-MSG-05 | MVP | 同一個 idempotency key 第二次送出 → 回傳第一次的項目 ID，不新增第二筆（照抄 OMB-5：保留原本那筆）。Agent Mail 是否原生支援 **待確認**；不支援時由 client 端處理，**待對齊 T7**。 | AC-02.4 |
| SR-MSG-06 | MVP | 問答／動手判定表（以收件端判定為準，G-03）：見下方決策表。 | AC-05.1、05.2 |
| SR-MSG-07 | MVP | 收件 agent 離線時，項目只保存為未讀；任何人或 agent 都不能代為執行或代答。 | AC-02.2、05.3 |
| SR-MSG-08 | MVP | 「已讀」＝收件 agent 實際取得這則項目（Agent Mail Rust 的 fetch 預設會標已讀，F-01b E2）。只想預覽不標已讀時，用 `mark_read=false`。 | AC-03.3 |
| SR-MSG-09 | 待確認 | 問答類的回答時限：G1 沒有決定。OpenMausBot 的做法是「單純問題不設逾時」（F-06 OMB-3）。決定前，FR-16 不實作也不驗收。 | AC-05.4 |
| SR-MSG-10 | MVP | 開工讀取（FR-09）一律在處理使用者第一個指令之前；Hub 連不上時要明說，不能當成「沒有新項目」。觸發方式（hook、指令）**待對齊 T7**。 | AC-03.1、03.4 |
| SR-MSG-11 | 待確認 | 撤回：寄件者在收件者讀取或回應前，可以送一則「撤回」標記給同一串；之後收件端只顯示「已撤回」，該請求不能再被同意。原文保留。（AC-02.3、06.5 仍待人工審查） | US-02、06 |

**SR-MSG-06 判定表**

| 請求內容 | 寄件者標記 | 收件端判定 | 例子 |
|---|---|---|---|
| 只問資訊，不改任何檔案或狀態 | question | question → 自動回答 | 「login 測試目前有沒有過？」 |
| 會寫檔、執行指令、接任務、合併、建分支 | 任意 | action | 「接下 Issue #12 並開分支」 |
| 同時有問題與動手 | 任意 | action | 「測試有沒有過？沒過就幫我修」 |
| 標 question 但內容要動手 | question | action（以收件端為準） | 「（question）順便把 README 改掉」 |
| 判斷不出來 | 任意／沒標 | action | — |
| 要求執行「讀檔並回報」 | question | question（只讀不改） | 「`package.json` 的 node 版本是多少？」 |

**訊息狀態**

| 狀態 | 進入條件 | 下一步 |
|---|---|---|
| 未讀 | 保存成功 | 收件 agent 取得 → 已讀；寄件者撤回 → 已撤回（待確認） |
| 已讀 | 收件 agent 取得 | 終點（動手類另開一個確認請求，見 2.3） |
| 已撤回 | SR-MSG-11 | 終點；原文保留 |

送出失敗不會有狀態，因為沒有保存任何東西。

### 2.3 確認請求（SR-CFM）

動手類請求在未開 auto mode 時，會在收件 agent 的畫面產生一個「確認請求」。S1 確認者＝維護者（Q-09，G1 #6）。

| 狀態 | 進入條件 | 資料副作用 | 寄件者收到 |
|---|---|---|---|
| 待確認 | 收件 agent 在線、畫面顯示確認提示 | 記錄顯示時間 | —（〔上線〕Discord 通知 維護者） |
| 已同意 | 收件人按同意 | 記同意者、時間；之後才開始執行 | 「已同意，開始執行」 |
| 已拒絕 | 收件人按拒絕（可附理由） | 記拒絕者、時間、理由；不執行 | 拒絕＋理由 |
| 已逾時 | 待確認滿 30 分鐘 | 記逾時時間；不執行；視同拒絕 | 逾時通知 |
| 已失效 | 收件 session 在待確認時結束（照抄 OMB-4） | 不執行 | 「對方 session 已結束，未執行」 |
| 已撤回 | 寄件者撤回（待確認，SR-MSG-11） | 不執行 | — |

| ID | 批次 | 規則 | 回指 |
|---|---|---|---|
| SR-CFM-01 | MVP | 只有「已同意」能讓動作開始。其他任何狀態，或狀態不明、紀錄寫不進去，都不執行（fail-closed）。 | AC-06.1 |
| SR-CFM-02 | MVP | 逾時從**確認提示顯示**時開始算，不是從送出時。收件人離線期間不計時；上線後顯示提示才開始算（AC-06.6）。 | AC-06.4、06.6 |
| SR-CFM-03 | MVP | 滿 30 分鐘（≥ 30:00）即逾時；29:59 時按的同意仍有效；逾時後再按無效，畫面提示「已逾時」。 | AC-06.4 |
| SR-CFM-04 | MVP | 確認結果（狀態、操作者、時間、理由）寫進 Agent Mail 同一串，寄件者能查到。 | AC-06.2、06.3 |
| SR-CFM-05 | MVP | 拒絕或逾時不會讓寄件 agent 整件事失敗：寄件 agent 收到結果後，跳過這個動作、繼續做其他能做的（照抄 OMB-2、OMB-3）。 | AC-06.3、06.4 |
| SR-CFM-06 | MVP | 一個確認請求只能被回應一次（照抄 OC-5：按鈕只用一次）。重複按下 → 顯示已處理的結果，不重複執行。 | US-06 |
| SR-CFM-07 | 待確認 | S1 是否也能從 Discord 按同意：PRD 只要求「在收件畫面確認」，Discord 只負責通知。決定前 Discord 不提供同意按鈕。 | AC-06.1、09.3 |
| SR-CFM-08 | 待確認 | session 結束時把待確認改成「已失效」是依 OMB-4 推導，PRD 沒有寫明。 | AC-06.5、04.3 |

### 2.4 auto mode（SR-AUTO）

| 狀態 | 進入條件 | 期間行為 |
|---|---|---|
| 未啟用 | 預設 | 動手類一律走確認 |
| 有效 | 收件人開啟，且通過 SR-AUTO-02 | 來自**指定對象**的動手類請求直接執行，每次都記錄並通知 |
| 已到期 | 伺服器時間 ≥ 結束時間 | 同未啟用；發「auto mode 已結束」通知 |
| 已關閉 | 收件人提前關閉 | 同未啟用；記錄關閉事件 |

| ID | 批次 | 規則 | 回指 |
|---|---|---|---|
| SR-AUTO-01 | 上線 | 只有收件 agent 的擁有者能開或關（S1＝維護者，在該 agent 的畫面操作）。其他人嘗試 → E-NOT-OWNER，不產生生效紀錄。 | AC-07.6、14.2 |
| SR-AUTO-02 | 上線 | 開啟時必須指定具體的 agent，不能指定「所有人」（一次能否指定多個：待確認）。時長沒填 → 1 小時；可填 1～240 分鐘的整數；0 或 >240 → E-AUTO。 | AC-07.1、07.7 |
| SR-AUTO-03 | 上線 | 結束時間＝開始時間＋時長，由伺服器計算。請求在結束時間**之前**到達伺服器 → 自動執行；在結束時間或之後到達 → 走確認。 | AC-07.4 |
